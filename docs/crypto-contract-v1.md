# Контракт шифрования текста v1

Для MSG-030 / [issue #4](https://github.com/OutSiders-Techniki/messenger-frontend/issues/4). Статус: проект для согласования. Утверждённая основа взята из переданного заказчику плана; точные форматы ниже, отсутствовавшие в плане, являются предложениями команды разработки.

## Основа из плана

Клиент-инициатор генерирует 32 случайных байта через crypto.getRandomValues. Это ключ AES-256, без PBKDF2 и без пользовательских фраз. Для каждого диалога используется отдельный ключ. Ключ передаётся второму участнику лично и не отправляется серверу. Перед импортом можно сохранить парольный файл с ключом; перенос файлом относится к Should и не блокирует текстовый MVP. После importKey ключ неизвлекаемый; хранится в IndexedDB по паре пользователь/диалог или только в памяти в режиме «не запоминать».

Шифрование — AES-256-GCM, новый случайный IV 12 байт при каждом новом шифровании. Пакет содержит `{v,id,sentAt,iv,ct}`, где ct включает тег. AAD собирается локально из версии, ID диалога, ID отправителя, ID сообщения и времени. Поля aad в пакете нет. Сообщения не сохраняются на диск клиента.

## Ключ и контрольная сумма

Использовать Base32 RFC 4648 с алфавитом `ABCDEFGHIJKLMNOPQRSTUVWXYZ234567`. Алфавит ключа не совпадает с алфавитом публичного ID: исключение I/O/0/1 относится к публичному ID, а не к стандартному Base32 ключа.

32 байта = 256 бит = 52 символа Base32 без `=`; последние четыре незначащих бита должны быть нулевыми. Контрольная сумма — первые 20 бит SHA-256 **исходных 32 байт**, от старшего бита к младшему, представленные четырьмя Base32-символами. Эквивалент: первые четыре символа Base32 полного SHA-256, а не Base32 hex-строки.

Итого 56 символов: 13 групп ключа по 4 и последняя группа checksum из 4. Предлагаемый отображаемый разделитель — дефис. Ввод допускает ASCII-пробелы, переводы строк, табуляцию и дефисы; ASCII a–z приводятся к верхнему регистру. Другие символы и Unicode-подмены отклоняются, I/O не заменяются цифрами. После нормализации: ровно 56 символов, декодируются первые 52, проверяются длина 32 байта, нулевые хвостовые биты и checksum. Несовпадение: «Проверьте ключ: неверная длина, символы или контрольная сумма».

Checksum выявляет случайные опечатки, но не подтверждает личность собеседника и не защищает от умышленной замены ключа. Передача лично остаётся частью схемы.

## Предлагаемые типы и кодирование

| Значение | Формат v1 |
|---|---|
| v | JSON-число 1; неизвестные версии отклонять |
| id | Клиентский UUID v4, нижний регистр, дефисы; генерируется до шифрования |
| sentAt | Неотрицательное безопасное целое число: миллисекунды Unix UTC, не строка и не секунды |
| dialogId | Стабильная строка ID диалога из API |
| senderId | Стабильный публичный ID отправителя; backend берёт его из сессии |
| iv | 12 байт, кодированные Base64url без `=`; ровно 16 символов |
| ct | Base64url без `=` от ciphertext || tag; tagLength = 128 бит, последние 16 байт — тег |
| plaintext | UTF-8 текста без BOM; не нормализовать Unicode и переводы строк скрытно |

Для dialogId и senderId предложить ASCII `[A-Za-z0-9_-]{1,128}`. Если бэкенду нужен другой формат, согласовать его до реализации, а не удалять символы на клиенте. Регистр ID сохраняется как возвращён сервером. Base64url декодировать строго: допустимый алфавит, длина и нулевые хвостовые биты; повторное кодирование должно совпасть с входом.

Предлагаемый лимит текста — 16 384 байта UTF-8; требует подтверждения команды и не заменяет согласованный лимит медиа 25 МБ. Для непустого текста ct имеет от 17 до 16 400 декодированных байт. Ограничение считать в байтах, не в JavaScript string.length. Пробельные сообщения запрещает UX, но их не преобразует криптомодуль.

## Канонические байты AAD

Предложение: UTF-8 от компактного JSON-массива в фиксированном порядке:

```javascript
JSON.stringify([1, dialogId, senderId, id, sentAt])
```

Никаких пробелов, BOM, перевода строки в конце, перестановки полей, округления даты или преобразования ID. Все входы сначала валидируются. ASCII-ограничения ID исключают различия Unicode-экранирования между JS и .NET. Дата сериализуется целым десятичным числом без экспоненты. Для тестового примера точная строка:

```json
[1,"dialog-test-1","USERAB23","00000000-0000-4000-8000-000000000001",1794463200000]
```

Для приёма сервер возвращает внешний объект `{dialogId,senderId,envelope:{v,id,sentAt,iv,ct}}`; envelope сохраняется без изменения значений. При отправке dialogId берётся из маршрута, senderId — из авторизованной сессии. Внешняя обёртка — предложение для DTO/SignalR, а не дополнительное поле aad. Сервер не может заменить sentAt своим временем; серверное время при необходимости передаётся отдельным полем и не участвует в AAD v1.

AAD связывает расшифровку с этим контекстом. Общий симметричный ключ не даёт доказательства авторства против другого владельца того же ключа. Подмена senderId сервером без ключа нарушит проверку тега, но участник с ключом способен создать новый шифротекст.

## Отправка, приём и повтор

1. До шифрования проверить доступность ключа и контекст. Создать id и sentAt один раз; сгенерировать случайный IV. Для ключа нельзя повторять IV при новом шифровании. Случайная генерация даёт вероятностную уникальность; срок жизни ключей и предельное число сообщений требуют отдельной эксплуатационной политики.
2. Собрать AAD, зашифровать и сформировать envelope. При повторе доставки отправлять **тот же пакет**, а не повторно шифровать изменённый текст под тем же id/IV.
3. Backend проверяет сессию, участие в диалоге, типы и размер. Уникальность записи — `(dialogId,senderId,id)`. Идентичный повтор возвращает прежний результат, другой пакет с тем же ключом идемпотентности — конфликт, без перезаписи ciphertext. Согласовать транзакционную реализацию с Егором.
4. Получатель проверяет контекст, типы, кодирование и ограничения; выбирает ключ своего аккаунта и диалога; собирает AAD и проверяет GCM. Только после успешной проверки добавляет сообщение в ленту и помечает id обработанным в рамках диалога.
5. Неверный ключ, изменённый AAD, IV, ciphertext или tag: «Неверный ключ или сообщение повреждено». Не показывать промежуточный текст. Если ключа нет, показать запрос ввода ключа, а не сообщение о повреждении.
6. Повтор успешного id не добавляет второй элемент. Повреждённая первая доставка не должна навсегда блокировать последующую корректную. Отсев повтора — логика приложения, не свойство GCM; перезагрузка и reconnect требуют синхронизации с сервером, включая удаления.

## Совместимость и границы

В WebCrypto результат AES-GCM содержит ciphertext и tag вместе. В .NET при отдельном API для тега нужно выделить последние 16 байт; строки Base64url не подавать как байты шифротекста. `extractable:false` запрещает экспорт ключа API, но не запрещает исполняющемуся в origin вредоносному JS пользоваться ключом, поэтому CSP и защита от XSS остаются обязательными.

Медиа — Must; этот документ задаёт только текст. Для файла и его зашифрованных метаданных нужны отдельные IV, согласованный AAD с различением типов данных и отдельные ограничения загрузки; это MSG-038. Не применять текстовый лимит к медиа и не создавать самовольно несовместимую схему. 25 МБ согласованы для исходного файла; точное число байт и транспортный запас на tag/кодирование ещё предстоит зафиксировать с backend.

## Матрица проверок

| Проверка | Ожидаемый результат |
|---|---|
| Общий вектор JS / .NET | Совпадают байты AAD, checksum, ciphertext и tag |
| Ключ после Base32 encode/decode | Те же 32 байта |
| Замена символа / неверная длина / ненулевые хвостовые биты | Отказ до importKey |
| Другой ключ | Отказ GCM без открытого текста |
| Изменение dialogId, senderId, id, sentAt | Отказ GCM |
| Изменение IV, ciphertext или tag | Отказ GCM |
| Неизвестная версия / неверное кодирование | Отказ до расшифровки |
| Две доставки одного пакета | Один элемент ленты |
| Два новых шифрования одинакового текста | Новые IV; не рассчитывать на одинаковый ciphertext |

Контрольный пример: `fixtures/crypto-v1.json`. Он использует публичные фиксированные ключ и IV только для сравнения реализаций, никогда для реальной переписки. Проверка Node: `node scripts/verify-contract.mjs`. Это проверка примера спецификации, не готовый crypto.js и не закрытие MSG-035.
