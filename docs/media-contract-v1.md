# MSG-38. Шифрование вложений v1

Клиент отправляет одно фото или видео на сообщение. Имя, MIME и подпись
шифруются вместе. Сервер видит идентификаторы, время загрузки, размер
файла, зашифрованные метаданные и зашифрованные байты файла.

## Пакеты и ключ

Клиент использует неизвлекаемый ключ AES-256-GCM диалога. Для пакета
сообщения, файла и метаданных генерируются отдельные случайные 12-байтные
IV. Тег каждого пакета занимает 16 байт.

1. По [текстовому контракту v1](crypto-contract-v1.md) клиент шифрует пустой
   массив байтов. Аутентифицированный пустой текст обозначает вложение.
   Обычный текст шифруется без изменений, пустой текст в обычном сообщении
   не отправляется. Идентификатор вложения совпадает с UUID сообщения.
2. AAD для файла и метаданных кодируется как UTF-8 от компактного JSON
   `["graphen/media",1,part,messageAAD,attachmentId]`. Значение `part`
   равно `"file"` или `"metadata"`. `messageAAD` является **строкой**
   компактного JSON `[1,dialogId,senderId,messageId,sentAt]` из текстового
   контракта. `sentAt` задаётся целым числом миллисекунд Unix. Идентификаторы
   берутся из исходного сообщения, регистра символов не меняют.
3. Тело загрузки — ciphertext файла без последних 16 байт тега.
   Размер тела равен размеру исходного файла и составляет 1–25 000 000 байт.
4. Метаданные — UTF-8 JSON с полями `name`, `mime`, `caption`, `fileIv`
   и `fileTag`. Поля `fileIv` и `fileTag` кодируются обычным Base64 с
   заполнением. Метаданные шифруются и упаковываются как
   `0x01 || metadataIv (12 байт) || metadataCiphertext || metadataTag (16 байт)`.
   Двоичный пакет занимает до 16 384 байт и передаётся в обычном Base64.

## REST

Сначала клиент отправляет обычный пакет сообщения. Затем отправитель
вызывает `POST /dialogs/{dialogId}/messages/{messageId}/attachments/{attachmentId}`.
В теле идут зашифрованные байты с типом `application/octet-stream`, в
заголовке `X-Attachment-Metadata` — зашифрованные метаданные в Base64.

Сервер связывает сохранённый шифротекст с обеими существующими копиями
сообщения. Каждый участник читает метаданные по тому же URL через `GET`
и получает байты через `GET …/{attachmentId}/content`. Посторонний и
участник, удаливший свою копию, получают 404. Удаление последней копии
ставит шифротекст в очередь физического удаления.

Получатель восстанавливает AAD из сообщения, проверяет и расшифровывает
метаданные, добавляет `fileTag` к полученным байтам и проверяет тег при
расшифровке файла. Имя и подпись вставляются в интерфейс как текст. При
ошибке аутентификации содержимое не показывается.

Запись о сообщении может появиться раньше файла. Если загрузка прервалась,
отправитель может повторить тот же пакет из открытой вкладки. Ответ 409
считается подтверждением повтора после сверки зашифрованных метаданных и
размера. Очередь повторной отправки хранится только в памяти вкладки.
